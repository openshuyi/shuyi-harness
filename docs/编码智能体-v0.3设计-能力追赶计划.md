# 编码智能体 v0.3 —— 能力追赶计划（设计文档）

> 对应 gap 分析：《对比 OpenCode 还有哪些差距》的结论落地。
> 目标读者：后续会话中负责实现的开发智能体。本文只定义**做什么、为什么、怎么做**，不重复 v0.2 已有设计（见 `docs/` 下三份 v0.x 文档）。
> 里程碑编号 M1–M6 即开发优先级排序，建议按序实施，每个 M 独立可交付、独立可测试。

## 0. 设计总则

延续 v0.2 的三条铁律，所有新增能力不得违反：

1. **事件溯源**：一切状态变更都是事件追加；事件模型「只增不改」（新事件追加、payload 只加可选字段）。
2. **权限 fail-closed**：Loop 调用任何工具前必须经过 PermissionService；任何新增工具必须声明权限级别并接入裁决。
3. **本地优先**：不引入必须联网才能工作的核心路径；联网能力（M4）必须可配置开关且默认有 mock/降级路径。

另外两条 v0.3 新增约束：

4. **向后兼容**：v0.3 不得破坏 v0.2 的事件日志与 SQLite schema，只允许 `ALTER TABLE ADD COLUMN` 与新事件类型。
5. **每个 M 结束后项目必须可运行**：`bun run dev:server` + `bun run dev:web` + `bun test` 全绿。

## M1. 任务清单工具（todowrite / todoread）

**动机**：长程多步任务中，模型缺乏显式进度结构，容易遗漏步骤或重复劳动。OpenCode 将其列为一级工具与一级权限项。

### 设计

**工具定义**（加入 `apps/server/src/tools/todo.ts`）：

```ts
todowrite: args = { todos: TodoItem[] }
// TodoItem = { content: string, status: "pending" | "in_progress" | "completed", priority?: "high"|"medium"|"low" }

todoread: args = {}
// 返回当前会话全部 todo（含状态），按 in_progress > pending > completed 排序
```

**语义规则**：
- todo 列表是**会话级**状态，存放在 Loop 上下文（不写入事件日志的每条消息里，而是独立维护 + 事件通知）。
- 每次 `todowrite` 调用为**全量覆盖**（模型重写整个列表），简化合并逻辑。
- 工具权限级别：`always-allow`（无副作用，不读写文件系统）。
- 列表注入 prompt 的方式：compaction 时作为保留项；每个 loop 迭代开始时若列表非空，注入 system 附录（截断到 30 项，超出提示模型精简）。
- 子代理（task）不继承父 todo 列表，返回摘要即可。

### 事件模型新增

在 `packages/types/src/events.ts` 追加：

```ts
export const TodoListUpdatedPayload = z.object({
  todos: z.array(z.object({
    content: z.string(),
    status: z.enum(["pending", "in_progress", "completed"]),
    priority: z.enum(["high", "medium", "low"]).optional(),
  })),
});
// 事件类型 key: "todo.list_updated"
```

- 只增不改；SSE 推给 Web 端用于渲染任务清单面板。
- 事件 store 存该事件，回放时自然包含 → 无需额外处理。

### Web UI

- `Trajectory.tsx` 旁新增可折叠「任务」面板：显示当前清单、完成度进度条、每项状态图标。
- 状态变更通过 SSE `todo.list_updated` 驱动 reducer（`core/reducer.ts` 加 case）。

### 验收

- e2e：`!todowrite ...` 后清单面板出现并随 `!todoread` 返回正确数据。
- 单元：全量覆盖语义、排序规则、compaction 保留。

## M2. 代理配置化（AgentDefinition 升级）

**动机**：v0.2 中 build/plan 是硬编码在 Loop 里的模式判断；OpenCode 的 agent 是「prompt + 模型 + 权限」三者可配的运行时实体。把模式判断下沉为配置，是 M3（按代理权限）与多代理并行（M5）的前置。

### 设计

**AgentDefinition 扩展**（改造 `apps/server/src/agents/index.ts`）：

```ts
export interface AgentDefinition {
  name: string;                    // "build" | "plan" | 用户自定义
  description: string;
  prompt: string;                  // system prompt（markdown 支持）
  model?: string;                  // 覆盖会话默认模型；缺省继承
  tools?: string[];                // 白名单；缺省 = 全量
  permissionOverride?: PermissionRule[];  // 见 M3
  source: "builtin" | "project" | "runtime";  // project: .agent/agents/*.md；runtime: API 动态添加
  modeDefault?: "plan" | "build";  // plan 代理等价于旧 plan 模式
}
```

**内置代理**（`builtin`，替代硬编码模式）：

| name | prompt 要点 | 特殊 |
|---|---|---|
| `build` | 现有 build system prompt | 默认代理 |
| `plan` | 只读分析，给出计划 | `tools` 中剔除 write/edit/bash；等价旧 plan 模式 |

**项目级定义**：`.agent/agents/*.md`（沿用现有 `parseAgentMarkdown` 格式，扩展 frontmatter 字段：`model`、`tools`、`permission`）。启动时扫描，支持热更新（mtime 监听可选，M2 先做启动扫描）。

**运行时定义**：`PUT/DELETE /api/agents/:name`（body = AgentDefinition JSON），持久化到 `~/.agent/agents.json`（与 models.json 同款模式）。`source: "project"` 与 `source: "builtin"` 只读。

**会话绑定**：SessionCreatedPayload 增加可选字段 `agent: z.string().optional()`（只增不改）；切换代理 = 追加 `session.config_changed` 事件 + `agent` 可选字段。Loop 每轮迭代从会话当前代理定义取 system prompt、工具白名单、模型覆盖。

**task 工具联动**：`spawnSubagent(task, parentCallId, agentName)` 中 `agentName` 可指向任意已加载 AgentDefinition，不再限于内置两类。

### 事件模型新增

```ts
// SessionConfigChangedPayload 追加可选字段：
agent: z.string().optional(),   // 切换当前代理

// 新事件：
export const AgentDefinitionUpsertedPayload = z.object({
  name: z.string(),
  definition: z.object({ ...AgentDefinition 的 zod 形态... }),
});
// key: "agent.definition_upserted"
```

### API

- `GET /api/agents` — 列出全部定义（builtin + project + runtime）
- `PUT /api/agents/:name` / `DELETE /api/agents/:name` — 仅 runtime 来源可写

### Web UI

- Composer 旁增加代理选择器（下拉），显示当前代理名与 description 提示。
- `ModelManager.tsx` 同款风格新增「代理管理」面板（增删 runtime 代理）。

### 验收

- e2e：切换 plan 代理后 write 工具在工具面消失（等价旧 Plan 模式行为）。
- e2e：`!task xxx` 指定自定义代理，子代理使用其 prompt/模型。
- 单元：project 代理优先级（同名 runtime > project > builtin 不覆盖 builtin——builtin 永远存在，同名 project 代理报错提示改名）。

## M3. 权限系统细粒度（glob 模式 + 按代理覆盖）

**动机**：v0.2 权限规则粒度是「工具 + 路径前缀」；需要支持 `*.test.ts` 这类 glob、按工具参数区分（bash 命令模式）、以及 M2 的按代理覆盖。

### 设计

**规则模型**（改造 `apps/server/src/permission/index.ts`）：

```ts
export interface PermissionRule {
  tool: string;                        // "bash" | "edit" | "write" | "*" 
  pattern: string;                     // 作用对象的匹配模式
  patternType: "glob" | "regex" | "prefix";
  matcher?: (args: Args) => string;    // 可选：从 args 提取被匹配字符串，缺省用 involvedPaths 第一个
  decision: "allow" | "ask" | "deny";
  source: "deny_builtin" | "user_config" | "agent" | "remembered";
}
```

**glob 匹配**：引入 `picomatch`（Bun 原生支持，零额外运行时成本）。规则按 `source` 优先级裁决（沿用现有「先命中先生效」顺序，见 permission/index.ts 头注释）：

1. `deny_builtin`（敏感路径，不可覆盖）
2. `agent` 代理覆盖规则（M2 注入，仅当前代理生效）
3. `user_config`（`~/.agent/permissions.json` + 项目 `.agent/permissions.json`，项目级优先）
4. `remembered`（会话期记住规则，现有逻辑不变）
5. 工具声明权限级别 + 沙箱等级
6. 默认拒绝

**bash 命令模式**：`matcher` 对 bash 提取完整命令行字符串，规则如：

```json
{ "tool": "bash", "pattern": "rm -rf *", "patternType": "glob", "decision": "deny" }
```

**Web UI**：ApprovalDialog 增加「记住规则」的高级选项：记住粒度可选「此命令/此路径」或「glob 模式」（用户手输）。`ModelManager` 同款面板新增「权限规则」页。

### 验收

- 单元：`picomatch` 规则匹配矩阵（大小写、`**`、否定模式 `!` 不支持——保持简单）。
- e2e：`.agent/permissions.json` 中 `"tests/**": "allow"` 后 `!write tests/foo.ts x` 免审批；`rm -rf` 规则 fail-closed 命中。

## M4. 联网能力（webfetch / websearch）

**动机**：模型无法获取当前项目外的知识（文档、报错信息、最新库版本）。

### 设计

**配置**（`mcp.json` 同款位置新增 `~/.agent/net.json`，可选）：

```json
{
  "webfetch": { "enabled": true, "maxBytes": 100000, "timeoutMs": 15000 },
  "websearch": {
    "enabled": false,
    "provider": "tavily",
    "apiKeyEnv": "TAVILY_API_KEY",
    "maxResults": 5
  }
}
```

缺省（无配置）时：webfetch 可用（纯 fetch，无害），websearch 工具**不注册**（工具面不出现，模型不会调用）。`enabled: false` 同理不注册。这就是默认降级路径。

**工具定义**（`apps/server/src/tools/web.ts`）：

```ts
webfetch: args = { url: string, format?: "markdown"|"text"|"html", maxBytes?: number }
// 拉取 URL → HTML 转 markdown（自研轻量转换：去 script/style/nav/footer，保留正文与代码块）
// 权限级别："always-ask"（出站请求必须用户可见；局域网地址 127.0.0.0/8、10/8、192.168/16 直接 deny 内置规则）

websearch: args = { query: string, maxResults?: number }
// 调 provider REST API，返回 [{title, url, snippet}] 列表
// 权限级别："always-allow"（只出站查询无副作用），但 tool 注册与否受配置控制
```

**安全红线**：
- webfetch 的 deny 内置规则禁止内网地址与 `file://` 协议（SSRF 防护）。
- 返回内容统一截断（沿用 MAX_OUTPUT 32KB 策略）。
- 两个工具对子代理默认隐藏（`tools` 白名单控制）。

### 事件模型

复用现有工具调用事件，**无新增事件类型**。

### 验收

- 单元：HTML→markdown 转换（代码块、表格、链接保留）；SSRF 地址判定矩阵。
- e2e（mock fetch）：`!webfetch https://example.com` 通过；内网地址被拒。

## M5. 多会话并行（服务端 + Web UI）

**动机**：OpenCode 支持同项目多 agent 并行会话；v0.2 的 SessionList 是切换式单活跃会话。依赖 M2（每会话独立代理/模型配置）与 M1（每会话独立 todo）。

### 服务端设计

`SessionManager`（`session/manager.ts`）现状已管理多会话对象，改动点：

1. **并发 Loop**：每个会话一个独立 Loop 实例与异步任务，互不阻塞（现有结构已支持，验证即可）。
2. **事件总线过滤**：`bus/index.ts` 订阅带上 `sessionId`，SSE 客户端按订阅的会话集合过滤推送；支持客户端订阅多个会话（`GET /api/sessions/:id/events` 保持单会话流，新增 `GET /api/events?sessions=a,b,c` 聚合流，内部按 sessionId 分派）。
3. **SQLite 并发写**：event-store 写入加 `BEGIN IMMEDIATE` 事务（Bun 的 `bun:sqlite` 单写者天然串行，验证即可，补测试）。
4. **API**：
   - `POST /api/sessions` 支持 `agent` 字段（M2 定义）。
   - `GET /api/sessions` 返回每会话 `status`、`activeCallCount`、`agent`、`model`（列表项信息增强）。

### Web UI 设计

- **SessionList 改造**：每项显示状态徽标（idle/running/awaiting_approval 圆点）、当前代理名、「+ 新会话」支持选择起始代理。
- **并行视图**：新增「分栏模式」开关——点击会话项上的「⇄」后，主区域左右分栏同时渲染两个会话的 Trajectory，各自独立 Composer。分栏仅支持 2 栏（简化 reducer 与布局；超过 2 个活跃会话仍是切换式）。
- **通知**：非活跃会话产生 `approval_requested` 时，SessionList 对应项闪烁提示（reducer 在聚合流中收到其他会话事件时更新列表状态，不渲染详情）。

### 事件模型

无新增类型；`SessionRecord`（只增不改）追加可选字段 `agent: z.string().optional()`。

### 验收

- e2e：两个会话同时跑 mock 模型流式输出，分栏各自渲染互不串流；A 会话等待审批时 B 会话可继续。
- 单元：聚合 SSE 流按 sessionId 分派；event-store 并发追加不丢事件。

## M6. ACP 协议接入（IDE 前端）

**动机**：让 VS Code / Zed 等 IDE 通过 ACP（Agent Client Protocol）把本服务端当作 agent 后端，复用全部已有能力（工具、权限、事件流），而非另做 TUI。

### 设计

**新模块**：`apps/server/src/acp/`。

- `index.ts` — ACP JSON-RPC 2.0 over stdio 入口（`bun run apps/server/src/acp/index.ts` 启动；同时提供 `agent-bin --acp` 子命令，M6 顺带接入 `build:binary`）。
- 协议映射表（ACP ↔ 内部事件）：

| ACP 方法/通知 | 内部对应 |
|---|---|
| `initialize` | 握手：返回 capabilities（fs 读写、bash、工具列表） |
| `session/new` | 创建 Session（`session.create`） |
| `session/prompt` | 追加 MessageUser → 启动 Loop |
| `session/update` (agent→client) | SSE 事件流 → ACP 通知（text delta / tool call / plan/todo 更新） |
| `session/request_permission` | `ApprovalRequested` → IDE 弹窗 → `ApprovalResolved` |
| `fs/read_text_file` 等 | 复用现有 read/write/edit 工具实现（去掉权限包装，IDE 客户端自身裁决） |

- **权限桥接**：ACP 模式下 PermissionService 的 verdict 不再走 Web ApprovalDialog，而是经 `session/request_permission` 发给 IDE；fail-closed 语义不变。
- **能力裁剪**：ACP 客户端声明的 capability（`fs: readOnly` 等）映射为会话沙箱等级。

### 范围控制（M6 内不做）

- 不做 TUI 客户端。
- 不做 ACP 的 terminal 复用（terminal/create 由 IDE 侧处理，agent 只用 bash 工具）。
- 不做云端 share link（已有离线 HTML 回放）。

### 验收

- e2e：stdio mock 客户端完成 initialize → session/new → prompt → 收到 text delta → 请求一次权限 → 会话结束。测试用 `test/fixtures/acp-mock-client.ts`。
- 手动：Zed 编辑器配置 ACP 命令指向 `agent-bin --acp`，可完成一轮问答 + 一次 bash 审批。
